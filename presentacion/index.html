El mito de que los ORMs impiden la inyección SQL

Explotación en vivo de dos vulnerabilidades reales de TypeORM y su defensa con Zod y lista blanca.

Andrea Sarmiento Paredes · Iñaki Vidal Alonso
Node.js · Express · TypeScript · TypeORM · Zod

01 · Conceptos previos

¿Qué es una inyección SQL?

La app habla con su base de datos mediante consultas SQL. Hay inyección cuando lo que escribe el usuario deja de tratarse como un dato y se ejecuta como una orden. Así, un atacante puede leer, modificar o borrar datos que no le corresponden.

Un buscador de usuarios por nombre

aliceLa app busca a alice. Correcto.
' OR '1'='1El filtro se rompe y devuelve a TODOS los usuarios.

La defensa clásica: parametrizar

SELECT * FROM user WHERE username = ?
// el valor viaja aparte, nunca como código

Funciona para valores (nombres, números), pero no para el nombre de una columna ni para la forma del dato. Esos dos huecos son los que explotan los CVE de hoy.

01 · Conceptos previos

¿Qué es un ORM y por qué confiamos en él?

Un ORM (Object-Relational Mapping) es una librería que traduce los objetos de tu código a SQL, para no escribir las consultas a mano.

La falsa sensación de seguridad

repo.findBy({ username: "alice" })
// TypeORM lo convierte en SQL seguro:
WHERE "username" = ?
findBy({...}) pides datos con un objeto; no escribes SQL a mano.
= ? el valor «alice» viaja aparte (parametrizado): no puede ejecutarse como código.

El ORM solo parametriza el caso simple → el programador relaja los controles.

Pero el mito se rompe

qb.distinctOn([req.body.distinctOn]);
await repo.save(req.body);
distinctOn([req.body…]) mete el texto del usuario como nombre de columna, sin validar → CVE-2026-76848.
save(req.body) guarda el cuerpo entero de la petición tal cual, sin comprobar tipos → CVE-2025-60542.
  • Va a un sitio que no admite ? (un nombre de columna).
  • El dato llega con una forma inesperada (un objeto donde esperaba texto).

03 · Vector 1 · CVE-2026-76848

El buscador que ejecuta SQL ajeno — distinctOn()

distinctOn() agrupa los resultados por una columna para no repetir filas.

El nombre de una columna no admite ?, así que TypeORM lo pega como texto:

const qb = repo.createQueryBuilder("user")
  .where("user.visibleEnDirectorio = 1");

if (distinctOn)
  qb.distinctOn([distinctOn]);  // ❌ sin validar
.where(...) deja ver solo las cuentas visibles del directorio.
distinctOn([distinctOn]) pega el texto del usuario dentro del SELECT sin comprobarlo.

Lo que escribe el atacante en el buscador:

1), * FROM user WHERE role='admin' --

Qué hace ese texto, pieza a pieza

11) cierra el paréntesis que TypeORM dejó abierto.
2, * FROM user WHERE role='admin' pide todos los administradores.
3-- comenta (anula) el filtro que ocultaba la cuenta.

Dato técnico: en TypeORM real el fallo está en SelectQueryBuilder (PostgreSQL): interpola la columna sin lista blanca.

04 · Vector 1 · solución (API v2.0)

Mitigación con lista blanca de columnas

Validar con Zod ANTES de TypeORM

// ANTES ❌ — cualquier texto entra
qb.distinctOn([distinctOn]);

// DESPUÉS ✅ — lista blanca de columnas
const ALLOWLIST = { id: "user.id",
  username: "user.username", department: "user.department" };

const Dto = z.object({
  distinctOn: z.enum(["id", "username", "department"]),
}).strict();

const r = Dto.safeParse(req.body);
if (!r.success) return res.status(400);   // corta aquí
qb.distinctOn([ ALLOWLIST[r.data.distinctOn] ]);
🎓Directorio
API v2.0
1), * FROM user WHERE role='admin' --Filtrar
HTTP 400 — Bad Request

Mismo ataque, bloqueado: 400 y no se ejecuta ninguna consulta.

  • Zod valida el valor contra la lista blanca.
  • safeParse corta con 400 si no encaja.
  • Solo la columna traducida llega a distinctOn.

05 · Vector 2 · CVE-2025-60542

El formulario que toca campos prohibidos — save()

save() guarda en la base de datos los campos del objeto que recibe.

El campo espera un texto; si envías un objeto, TypeORM lo convierte en varios cambios:

app.post("/api/vulnerable/perfil", async (req, res) => {
  const repo = getRepository(User);
  await repo.save(req.body);   // ❌
});
req.body es lo que mandó el usuario (aquí, el formulario de perfil).
save(req.body) guarda todas las claves que lleguen, sin comprobar su tipo.

Lo que escribe el atacante en «departamento»:

{"department":"Robótica","role":"admin"}

Qué pasa por debajo

1Esperaba un texto para department.
2Recibe un objeto con una 2ª clave: role.
3TypeORM también escribe role = 'admin', que no debía tocar.

Dato técnico: afecta a TypeORM < 0.3.26 con MySQL — la librería sqlstring (stringifyObjects:false) expande el objeto en columnas.

06 · Vector 2 · solución (API v2.0)

Mitigación exigiendo el tipo correcto

Zod rechaza lo que no es texto

// ANTES ❌
await repo.save(req.body);

// DESPUÉS ✅
const Dto = z.object({
  department: z.string().trim().min(2).max(60),
}).strict();   // objeto o clave extra → rechazado

const r = Dto.safeParse(req.body);
if (!r.success) return res.status(400);
// el id sale de la sesión, no del body (evita IDOR)
await repo.update({ id: req.session.userId }, r.data);

Bloqueado antes de tocar la base de datos.

  • z.string() exige texto: no admite objetos.
  • .strict() prohíbe claves de más (como role).
  • El id sale de la sesión: no puedes editar a otro usuario.
